## Problem Statement

Report numbers are produced by inline, undocumented formulas with inconsistent date semantics (snapshot vs ranged, all-time vs filtered, both-dates-or-ignore, issue-date vs payment-date, count vs rate). Two screens can disagree on "SLA compliance" for the same period. Nobody — operator, auditor, or developer — can tell which definition produced a number, and a future formula change would silently rewrite history. Access is one coarse `report.view` that opens revenue/MRR, asset, SLA and stock data to anyone who can see any report, so least-privilege roles (e.g. NOC: SLA/asset only; finance: business only) cannot be expressed. Original acceptance for the V2 cards was lost; only their three headline concerns (formula-version, granular capability, data dictionary/KPI definitions) survive in titles.

## Solution

Introduce, inside `Modules/Reporting`, (1) a code-defined **metric definition registry** — one definition object per KPI (key, label, formula text, unit, source tables/columns, date basis, snapshot-vs-ranged, scope, report(s), `formula_version`), exposed read-only to the UI and the data dictionary; (2) a **formula version** carried in every report payload (`formula_version` per report/metric) so numbers are attributable and any future formula change requires a version bump (+test); (3) **granular, report-level capabilities** `report.{business|asset|sla|stock_card|dictionary}.view`-style permissions (final names per owner decision), with `report.view` kept as the index/legacy umbrella and seeded role grants preserving current effective access unless the owner chooses otherwise; and (4) a **data dictionary page** under Reports listing every KPI definition and each source table/column used. The UI shows definitions (info tooltip/panel) next to KPI cards and a dictionary page. Existing computed values are NOT changed under version `v1` ("as-is" formulas recorded truthfully, including their quirks); any corrections (e.g. SLA by_category filtered, partial-date handling) ship only as an explicitly named `v2` after owner approval.

## User Stories

1. As an auditor, I want every report response to state its `formula_version` so I can tie a number to the definition that produced it.
2. As a finance manager, I want Revenue (Paid) to state exactly which date it uses (issue date vs payment date) and which invoice statuses it includes, so I can reconcile to ledgers.
3. As an operator, I want each KPI card to show a short definition (formula, date basis, snapshot vs period) so I do not misread MRR (a snapshot) as period revenue.
4. As an operator, I want a Data Dictionary page listing every KPI, its formula, source table/columns and owning report, so I can answer "where does this number come from".
5. As an admin, I want to grant a NOC user SLA and Asset reports without granting Business (revenue/MRR) or Stock Card.
6. As an admin, I want to grant finance users Business without Audit Log, and Audit Log properties without exposing the whole report suite.
7. As an admin, I want the role/permission screen to list the new `report.*` permissions in the existing `report` group.
8. As an existing staff user, I want my current report access unchanged after upgrade (staff still sees business/asset/sla/stock-card) unless the owner explicitly narrows it.
9. As a user without a report's capability, I do not see its card/menu entry and direct URL access returns 403 (no UI-only gating).
10. As a technician, I still only reach my own Technician Performance (no change in behavior or permissions).
11. As a developer, changing a KPI formula without bumping its version fails a test (definition registry vs query contract).
12. As a tenant admin, the dictionary and definitions are identical across tenants but every number remains scoped to my company.
13. As a user in the Indonesian-language UI, dictionary text follows the existing report page language conventions per owner decision (Business/SLA/Asset pages are English; Audit Log is Indonesian).
14. As a reviewer, I can verify each documented formula against a fixture-driven test with known expected values and date boundaries (last-day inclusive, one-sided date filters).

## Approved decisions

Applied by backend `t_1d565698` and UI `t_d698fabf` (implementation 2026-10-10). Every decision below uses the owner-approved RECOMMENDED option; none lacked a recommendation.

1. **Formula-version scope: (a) record-only.** Every metric is versioned `v1` = the formula exactly as the query implements it today. No query, filter, number or visual changed. Known quirks (snapshot vs period, both-dates-or-ignore range, issue date vs payment date, churn as a count, SLA `by_category` ignoring filters, Business SLA all-time) are recorded as `caveats` in the registry, not fixed. A report-level version is derived (`business.v1` = highest metric version of the report), so it cannot drift from the metrics.
2. **Capability names: (a) per-report view permissions.** New: `report.business.view`, `report.asset.view`, `report.sla.view`, `report.stock_card.view`, `report.dictionary.view`. Unchanged: `report.view` (now the Reports hub/index gate ONLY), `report.technician`, `report.manage`, `report.audit.view`. A user holding only `report.sla.view` can open `/admin/reports/sla` directly but not the hub; to get the hub, a role needs `report.view` as well.
3. **Registry location: (a) code registry + dictionary page.** `Modules/Reporting/app/Registry/` (`ReportType` enum = route/capability/title catalog, `MetricDefinition`, `MetricRegistry`, `MetricUnit`, `DateBasis`), versioned in git, no migration, no table. Read-only Inertia page `admin.reports.dictionary` (`Admin/Reports/Dictionary`) gated by `can:report.dictionary.view`; its content is static registry text (no queries, no company data, identical for every company).
4. **Audit Log capability: (a) keep single `report.audit.view`.** Route, `ReportFilterRequest`, `AuditLogResource` and the `can.export` / `can.view_properties` flags are untouched; no `report.audit.properties`, no export.
