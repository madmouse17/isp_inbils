# Push notifications (FCM) for the customer and technician apps

Status: ready-for-agent
Ledger: `docs/plans/INBILS_OMP_BACKLOG.md` → "ISP roadmap lanes (2026-10-12)" row `push-notifications`
Source: owner 2026-10-16: "pada download ada google-service.json untuk customer apakah bisa untuk firebase push notification, kurang apalagi jika ingin teknisi juga" → P1 "jadikan lane" = ya; P2 (assistant registers the apps and creates the service-account key in the owner's Chrome) = ya.

## Facts (2026-10-16)

- Firebase project `id-inbils-customer` (number 972813510161) now registers six Android apps: `id.inbils.customer{,.dev,.staging}`, `id.inbils.technician{,.dev,.staging}`. Combined `google-services.json` and the Admin SDK service-account key are at `~/.config/inbils/{google-services.json,firebase-service-account.json}` (outside both repos; the mobile `.gitignore` already ignores `google-services.json`). No SHA-1 needed (no Google Sign-In). No iOS target.
- Web: 19 notification classes; channels today are `database`, `mail`, `WhatsAppChannel`. The apps read `GET /api/v1/notifications` (database notifications) and `NotificationResource` already gives every notification a `type`, title, message and `subject {type, id}` deep link that the apps' routers consume. No device-token storage, no FCM sender, no `kreait` package in `composer.json`.
- Apps: no `firebase_core`/`firebase_messaging`, no `google-services` Gradle plugin, no `POST_NOTIFICATIONS` permission; both apps have `dev`/`staging`/`prod` flavors with `applicationIdSuffix`.

## Decisions (recommended, owner accepted the lane)

- **N1 Transport:** FCM HTTP v1 via `kreait/laravel-firebase` (new dependency; standard, maintained, needs the owner's approval per AGENTS.md — the owner approved the lane). Credentials path from `.env` `FIREBASE_CREDENTIALS=/path/outside/repo.json`; never in the repo; `.env.example` documents it; deploy compose mounts the file read-only.
- **N2 Token registry:** table `device_tokens` (`user_id` FK, `personal_access_token_id` FK → `personal_access_tokens` cascadeOnDelete, `app` enum customer|technician, `platform` android, `token` unique, `device_name`, `last_seen_at`, timestamps). Binding each device token to the Sanctum token that registered it means every existing revocation path (logout, password change, company suspension `revokeAll`, token expiry prune) also silences pushes: the channel only sends to device tokens whose access token still exists. `POST /api/v1/me/device-token` (upsert by token, per app, throttled) and `DELETE /api/v1/me/device-token` (on logout; the app also deletes its own token on sign-out). Tokens FCM reports as `UNREGISTERED`/`INVALID_ARGUMENT` are deleted on send. Cloud Messaging API (V1) must be enabled on the project; ticket 01 verifies with `inbils:push:test` and reports.
- **N0 Owner rule (2026-10-16): every action notifies the party concerned.** Mobile personas (technician, customer) get push + bell; web personas get bell and/or email. Events that lacked a database notification get one in this lane: technician — SPK assigned, SPK rejected, SPK approved, ticket first-response due; customer — visit completed, invoice issued, invoice due soon (3 days), invoice overdue, payment received. WhatsApp templates stay as they are.
- **N3 One push channel, same payload as the bell:** new `FcmChannel` that reads the notification's `toArray()` (the same data the bell shows) and sends `{notification: {title, body}, data: {type, subject_type, subject_id, notification_id}}` to every token of the recipient for the matching app (customer notifications → customer app tokens; technician → technician app tokens). Notifications opt in by listing the channel in `via()`; this lane opts in: ticket assigned / SLA breached / first response (technician), SPK assigned / rejected / approved (technician), technician en route / visit done / invoice due & overdue / payment received / announcement outage & maintenance (customer). Mail and WhatsApp unchanged. Promos never push (B3).
- **N4 Queued, idempotent, audited lightly:** sends run on the existing queue (`afterCommit`), one job per notification with up to 3 tries; failures logged with notification id and token suffix only; no message body in logs.
- **N5 App behaviour:** `firebase_core` + `firebase_messaging` in `inbils_core`; the Gradle `google-services` plugin in both apps with the combined `google-services.json` at `android/app/google-services.json` (gitignored; the owner copies it from `~/.config/inbils/`; CI/EAS not in scope); Android 13 `POST_NOTIFICATIONS` runtime prompt after first login (never before); token registered after login and on refresh; foreground messages shown as a local heads-up via `flutter_local_notifications` with one channel "Inbils" (importance high) and the ISP name as the title prefix; tap (background/terminated/foreground) routes through the existing notification subject router (`{type, subject_type, subject_id}`), then marks the notification read via the existing read endpoint. Opt-out: the OS notification settings (no in-app toggle in v1).
- **N6 Settings page:** none in v1. Company-level per-event toggles parked (`docs/PARKING_LOT.md`).
- **N7 Testing:** web feature tests with the Firebase messaging client faked (`Messaging` interface bound to a fake): token upsert/delete/ownership, channel payload per notification type, app routing (customer token never receives technician pushes), invalid-token cleanup, queued after commit; app widget tests: permission prompt timing, token registration call, tap routing from a data payload (foreground, background via `getInitialMessage` fake), local notification shown in foreground; device smoke on the AVD with the real FCM (send one test message via the console or `php artisan inbils:push:test {user}`).
- **N8 Order:** after `platform-superadmin` ships (its queue/compose work overlaps) and before `opaque-ids` (which converts `subject_id` to public ids in the same pass).
