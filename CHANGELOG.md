### Changed - Roles per company (2026-10-21)

- Lane `tenant-roles` (`.scratch/tenant-roles/design.md`, ADR-004, owner decision K15). Roles belong to a company: `roles.company_id` NOT NULL, `roles.template_key`, `App\Models\Role` with `BelongsToCompany`. Permissions stay one catalogue in code (`App\Support\PermissionCatalogue`). The migration copies every old global role into every company and remaps every user's assignments in each company he belongs to, and proves that no user's permissions changed. The five old roles are now Admin, Manajer, Staf, Teknisi and Pelanggan. NOC & Layanan Pelanggan, Gudang and Keuangan are added to existing companies with no users.
- **Permission checks.** Business rules check permissions, never role names. New markers: `app.web`, `app.technician`, `portal.access`, `evaluation.evaluable`, `report.technician.team`. A login without `app.web` lands on `/app-only`, or on "Akun ini belum punya akses aplikasi web". Code outside a company request uses `CompanyService::runAs`, `User::withPermissionIn` or `StaffRecipients::holding`.
- **Tenant.** Holders of `roles.manage` create, edit and delete their company's roles in Administrasi → Peran (Buat peran, Mulai dari templat, Hapus with Pindahkan ... pengguna ke). Guards: nobody grants a permission he does not hold, nobody edits a role or user richer than himself, SoD per company, the company keeps one active administrator, roles with users are moved before deletion, stale edits answer 409. Audited as `role.created`, `role.updated`, `role.deleted`. Pengguna lists members from other companies (badge Anggota) and sets their roles here with Atur peran.
- **Platform.** "Templat peran" replaces "Peran & hak akses" (`/platform/role-templates`); templates are copied once into new companies and never resynced, and the Admin template always keeps `roles.manage` and `app.web`. Per-company role repair sits on the tenant page (card Peran, `/platform/companies/{company}/roles`) behind step-up, audited in `platform` and `support`. `/platform/roles` is removed. The tenant export holds `roles.csv` and a `user_roles.csv` with `template_key`, not the role/permission pivots.
- **Security review fixes** (`docs/SECURITY.md` 2.6): user administration across companies needs coverage in every company of the target; deactivating or deleting a login keeps an administrator in each of its companies (company rows locked first); subsidiary role mirroring never grants more than the member holds at home; no role holds `portal.access` and `app.web` together; role audit rows land in the role's company; role writes drop the permission cache after commit and queue workers clear it before each job. The Users list costs a constant number of queries (35 at 7 or 31 rows; 106 and 414 before the fix).
- **Behaviour changes.** D1 access is additive (a technician who also holds `evaluation.view` sees all evaluations); D2 a login without `app.web` sees the no-access page; D3 non-administrators change only users and roles they cover; D4 assigning a ticket to a user without ticket permissions is a 422; D5 admin cards and invitations follow `roles.manage`; D6 billing alerts go to `roles.manage` holders incl. members; D7 subsidiary members get template-matched roles; D8 going home is always allowed; D9 the Staf template for new companies lacks `customer.create`.
- Deploy: maintenance window and backup, `migrate --force` (six migrations `2026_10_29_100000`-`100500`, self-checked), `config:cache`, `permission:cache-reset`, `queue:restart`. No mobile release. See `docs/operations/DEPLOYMENT.md` "Tenant roles release".

### Changed - Opaque public ids (ULID) in every URL and API payload; uniform 404; enumeration limiter (2026-10-17)

- Lane `opaque-ids` (`.scratch/opaque-ids`, tickets 01 to 05; ticket 06, the full gates and the release review, is still open). Authorization stays the control; opaque ids are a second layer against guessing and against reading record volume from a URL.
- What changed: every record that a URL, an API path, an Inertia prop or an API payload names is now addressed by its 26-character lowercase ULID `public_id`. Web and API routes bind by it (`whereUlid`), every resource and prop emits it as `id` and as each `*_id` reference, and every form and API request accepts it for reference fields and maps it to the integer key before the service layer. The integer `id` stays the primary key and every foreign key, and never leaves the server. The UI types are `string`, and the E2E helpers read ids from props.
- Old links break once (D6): an integer URL such as `/admin/customers/12` answers 404 now, so bookmarks must be reopened from the lists. Stored bell notifications are rewritten to the new ids; e-mail and WhatsApp links never carried ids.
- The apps must ship together with the server: the API contract is `docs/api/mobile-v1.openapi.json` version 1.1.0 (every `id` and `*_id` is a string; 99 type changes, no path or property added or removed). There is no dual-accept period. The customer and technician apps in `inbils-mobile` parse ids strictly as strings; a phone on an older build breaks on the first page, and a technician build with a v2 offline queue drops its unsent photos at the first start (drift schema 3).
- Midtrans: new payment attempts use the order id `INB-{ULID}` (30 characters, no company or invoice id). Lookups are unchanged; attempts created earlier keep their old id.
- Uniform 404 (K3): a record that does not exist, belongs to another company, or is hidden from the user by its policy answers the same 404 (policies return `Response::denyAsNotFound()`, hand-written checks use `App\Support\RecordNotFound`). A missing permission on a record the user may see, and page-level `can:` denials, stay 403. The API answer for another technician's work order is 404 now (it was 403).
- Enumeration limiter (K4): `App\Http\Middleware\DetectRecordEnumeration` on the web, platform and API groups counts record-level 404s per signed-in user (nobody who is signed out is counted) in a rolling window. Past the threshold it writes one `security.enumeration_suspected` audit entry (route name and ids tried) and answers 429 for the cooldown (JSON with `Retry-After` for the API, the "Terlalu banyak permintaan" error page for the web). 403s are never counted. Config `config/security.php`, env `SECURITY_ENUMERATION_ENABLED` (default on, off in `testing` and `e2e`), `SECURITY_ENUMERATION_THRESHOLD` (30), `SECURITY_ENUMERATION_WINDOW` (5 minutes), `SECURITY_ENUMERATION_COOLDOWN` (10 minutes).
- `TRUSTED_PROXIES` (`.env` or the container environment): behind a reverse proxy or load balancer set it (comma-separated addresses, CIDR ranges allowed, or `*` only when the proxy is the single way in) so the audit addresses, the per-address throttles and the generated URLs see the real client. `App\Http\Middleware\TrustConfiguredProxies` reads it on every request; empty, the default, trusts nobody.
- Security review fixes: signed-out visitors are no longer counted by the limiter (31 wrong isolir codes answered 429 on `/login` and `api/v1/auth/*` for the whole address); a web client that asks for JSON gets `{"message":"Not Found"}` for every 404 outside `api/*` (Laravel's own body named the model class and told a missing record from a hidden one); a list sent where one id belongs (`customer_id[]=5`) is refused by `ResolvesPublicIds`; `PublicId::new()` takes a random part per id (ids made in the same millisecond were consecutive); the subscriptions package filter takes the public id the page offers; a comment or a file on a ticket the user's role hides answers 404.
- Deploy: `php artisan migrate --force` in the same step as the code. The migrations add `public_id` to 59 tables in a chunked backfill and are safe to run again after a failure. The slow table is `activity_log`: the backfill updates its rows one by one, so on a large audit log the migration takes minutes (the time grows with the row count); put the site in maintenance mode, and take the backup first. Then `npm run build` and `php artisan queue:restart`, and release the apps.
- Not covered on purpose: human codes (`CUS-00001`, `INV-2026-00001`) stay visible to the owning company and still show volume where the template has a running counter (change it in Penomoran). `permissions`, `notifications`, `failed_jobs`, pivots, `settings` and framework tables keep their own keys. Public company logo files under `/storage/companies/<company_id>/...` still carry integer ids (open for the security review).

### Added - Automatic numbering with configurable format (2026-10-13)

- One page, Administrasi → Penomoran (`.scratch/number-sequences`), edits the code format of nine entities per company: invoice, SPK, subscription, network asset, ticket, inventory request, customer, employee number and product SKU. Each row has a prefix, a template, a next number, a reset period (never, yearly, monthly, daily) and a manual-input switch, and shows the next code as a live preview. The list is fixed (no "new type"); missing rows are created on first view or first use. Settings need `system.setting`; every edit is written to the audit log. Changing a format never touches existing codes.
- Templates are literal text (`A–Z a–z 0–9 - _ / .`) plus `{PREFIX}`, `{YYYY}`, `{YY}`, `{MM}`, `{DD}`, `{COMPANY}` (the company code) and exactly one `{SEQ:n}` (n = 1–10 digits, zero-padded, never cut). A yearly reset needs a year token, monthly also `{MM}`, daily also `{DD}`. Defaults: `{PREFIX}-{YYYY}-{SEQ:5}` for invoice (`INV`), SPK (`SPK`), subscription (`SUB`), network asset (`NA`) and ticket (`TKT`, yearly reset); `{PREFIX}-{YYYY}{MM}{DD}-{SEQ:4}` for inventory request (`REQ`, daily reset); `{PREFIX}-{SEQ:5}` for customer (`CUS`) and product (`PRD`); `{PREFIX}-{SEQ:4}` for employee (`EMP`). Rows that already existed keep their prefix and counter and produce the same codes as before.
- Engine: date tokens and period keys follow the company timezone (`companies.timezone`, the app timezone when blank). Generation takes the row lock inside the caller's transaction, so a rolled-back create gives its number back, and it skips any code already present in the entity's own table, soft-deleted rows included (it stops with an error after 1000 taken codes in a row: raise the next number on the page). A new row starts after the highest existing code that matches its format in the current period; free-form legacy codes are ignored unless they collide. Each module registers its entity in its service provider (`App\Support\NumberSequences\NumberSequenceRegistry`), so core imports no module model.
- Changed: `NumberSequenceService::generate()` lost its `$prefix` argument. New `peek()` (never null), `allowsManual()`, `resolve()` (a typed code only where manual input is on, else a generated one), `ensureAll()` and `update()`. `number_sequences` lost `padding` and `year_suffix` and gained `template`, `reset_period`, `period_key` and `allow_manual`; the migration converts each row to the template that yields its current codes. The Penomoran index no longer paginates or searches; the export route stays and now lists Template, Reset Period and Allow Manual.
